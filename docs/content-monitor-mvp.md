# Content Monitor MVP

第一阶段只建立本地、可替换、可验证的数据闭环，不自动发布、
不自动评论、不发送通知。优先使用免登录的公开数据；平台确实要求登录时，
只使用独立的本地采集账号，不使用主运营账号。

## 当前边界

- OpenCLI Admin 只负责发现公开作品、定时采集和保存原始数据。设计支持多平台、
  多对标账号，各平台逐个接通和验证。
- 同一作品首次出现时写入 `collected_records`；后续只在时序策略到期时写入新的
  `engagement_snapshots`，不再因内容去重而丢失应保留的互动数据变化。
- 统计检测器只执行确定性规则，不调用模型。每个平台下的每个对标账号单独计算基线，
  使用按发布时间排序的最近 20 条作品的主公开指标中位数代表日常水准。
- 最近 20 条中的广告、商业合作和疑似投流作品全部计入，不根据内容类型排除。
- 任一作品缺少已选定的主公开指标时，基线标记为数据不完整，
  不把缺失值当成零，也不使用第 21 条或更早作品补位。
- 新作品达到基线 3 倍为“火”，达到 5 倍为“特别火”。
- “火”的作品进入普通拆解与二创队列；“特别火”只提高处理顺序，
  不改变分析结论、脚本内容、选题数量或生成次数。
- 对标作品只使用公开可见的互动数据；点赞、收藏优先，评论、分享、播放等作为辅助信号。
  完播率通常属于账号自己的后台反馈，不作为对标作品的必需字段。
- 内置 AI 和通知默认关闭；平台分析、二创和发布反馈不属于第一阶段代码路径。
- Docker 服务默认只绑定 `127.0.0.1`，中心 API 不挂载 Docker 控制 Socket。

## 数据表

| 表 | 用途 |
|---|---|
| `content_accounts` | 对标账号的稳定身份 |
| `content_works` | 作品稳定身份与首次/最近发现时间 |
| `engagement_snapshots` | 每次采集看到的公开互动计数及完整原始数据 |
| `detection_results` | 账号基线、相对倍数、分类结果、是否进入分析以及优先标记 |

平台返回字段尚未验证，因此快照同时保存标准指标和完整 `raw_data`。每接通一个平台，
先使用实际能拿到的公开指标进行综合判断，不把完播率等仅账号本人可见的数据当作对标条件。

启用内容监控后，默认使用所有实际存在的公开互动指标；如果需要限制范围，
可以显式指定一个指标或指标列表，例如：

```json
{"content_monitoring": {"metric_name": "like_count"}}
```

也可以指定：

```json
{"content_monitoring": {"metric_names": ["like_count", "favorite_count", "share_count"]}}
```

缺少某一项公开指标不会淘汰作品。系统只对当前作品和最近20条作品中实际存在的指标
计算账号相对倍数；综合分使用可用指标的加权几何平均，点赞和收藏略高权重。
如果没有任何指标能形成可靠基线，才标记为“数据不足”。

## 作品观察接口与排序

统计结果通过只读接口提供给现有前端：

```text
GET /api/v1/content-monitor/works
```

可用参数：`queue=all|normal|priority`、`status`、`source_id`、
`account_id`、`page`、`limit`。`normal` 只返回“火”作品，`priority` 只返回“特别火”作品。
结果按“特别火优先 → 相对倍数从高到低 → 发布时间从新到旧”排序，
从而把特别火作品优先交给后续拆解层，但不改变检测结论。

现有 OpenCLI Admin 已增加“作品观察”只读页面。它只消费检测结果，
不会触发采集、登录、发布或通知。

页面同时支持导入对标账号：可逐行粘贴账号链接、使用“平台,账号链接”格式，
或上传文本/CSV/JSON。导入只建立账号身份，不自动登录、不自动采集；后续再为账号绑定
对应平台的数据源和采集方式。

抖音已增加作品分享链接导入：用户可粘贴整段分享文案，后端解析短链、读取作品详情，
反查作者 `sec_uid` 并保存已验证的账号身份。该入口使用本机 OpenCLI 浏览器会话，不读取、
不返回也不存储 Cookie。

## 抖音真实字段验证

- 可获取作者昵称、`sec_uid`、抖音号、作品 ID、文案、发布时间、时长、封面和视频地址。
- 可获取点赞、评论、收藏和分享数，并可读取作者最近 20 条作品与作品热门评论。

## 内容生成后的质检

本地已有三个可组合的质检 Skill：

- `dbs-ai-check`：识别 AI 写作痕迹，默认只诊断；
- `dbs-script-flow`：检查口播衔接、信息密度和完播风险；
- `dbs-resonate`：检查核心机制、受众共鸣和传播入口。

它们放在生成之后作为质检，不作为生成阶段的固定模板，也不把文案强行改成另一种“像人”的腔调。

## 前端改造边界

现有 OpenCLI Admin 前端就是产品界面的直接基础，保留当前的导航、卡片、
图表和列表框架，再按对标监控、作品筛选、内容拆解、二创和发布前检查改造内容。
不另行复刻或重建一套 UI。

## 新作品采集时序

1. 每 4 小时检查对标账号是否有新作品，不因此刷新全部历史作品。
2. 发现新作品后立即保存第一份快照。
3. 发布后 0–48 小时，每 4 小时保存一次快照。
4. 发布后第 3–7 天，每天保存一次快照。
5. 发布满 7 天时先保存第一份最终快照，随后停止自动更新。

早期快照只用于保存增长过程。正式爆款判定仅在最终快照到达后执行，
不使用 4 小时数据和 7 天数据直接比较。

当平台没有可用的发布时间，如何确定 48 小时和 7 天边界尚未确认，
因此时序策略当前要求显式传入 `published_at`，不自动猜测。
